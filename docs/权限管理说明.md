# 权限管理说明（现状）

> 适用范围：基于 JAVA 的智能体应用平台（amp）当前实现，对应代码与 `db/schema.sql`、`application.yml`。
> 相关设计稿：[IAM-RBAC方案](./IAM-RBAC方案.md)、[外部工具权限治理设计方案](./外部工具权限治理设计方案.md)。

---

## 1. 总览：四层权限模型

平台权限不是单一 RBAC，而是 **「谁能进管理面 / 谁能调哪个 Agent / Agent 能调哪些工具 / 工具以谁的身份调」** 四层叠加。

```text
┌─────────────────────────────────────────────────────────────┐
│ L1  接口准入（API Key / JWT / Jeecg）                        │
│     租户 · scope(open|admin) · Agent 白名单 · 人轨 RBAC      │
├─────────────────────────────────────────────────────────────┤
│ L2  智能体工具权限（Permission Rule / Mode）                  │
│     per Agent：ALLOW / ASK / DENY · DEFAULT / DONT_ASK       │
├─────────────────────────────────────────────────────────────┤
│ L3  人工确认 HITL（危险写 / ASK）                             │
│     approval_item · confirm · acceptRule 落库                 │
├─────────────────────────────────────────────────────────────┤
│ L4  工具侧鉴权（ToolMeta + 业务系统）                         │
│     risk / authMode / permCode / secretRef / user_token 透传  │
└─────────────────────────────────────────────────────────────┘
```

**设计原则**

| 原则 | 含义 |
| --- | --- |
| 租户隔离 | 一切数据与授权以 `tenantId` 为准，由 Key/JWT/Jeecg 解析 |
| 默认最小 | 未显式 ALLOW 的危险动作走 ASK 或拒绝；`admin` 不隐含 `open` |
| 双轨身份 | 机器走 API Key + scope；人走 JWT/Jeecg + RBAC 权限点 |
| 治理可审计 | 权限变更、审批、工具调用写 `audit_log` / `approval_item` |

## 2. L1 · 接口准入（身份与 Scope）

### 2.1 配置入口（`amp.auth.keys`）

```yaml
amp:
  auth:
    enabled: true
    keys:
      - key: s0-demo-key
        tenant-id: acme
        agents: ['*']          # 空 / * = 租户内全部 Agent
        scopes: [open]         # 业务对话、会话接口
      - key: s0-admin-key
        tenant-id: acme
        agents: ['*']
        scopes: [open, admin]  # 管理台 / 运维 / 审计 / 配额
```

| 字段 | 作用 |
| --- | --- |
| `key` | `Authorization: Bearer <key>` |
| `tenant-id` | 强制绑定租户（请求体可不传 tenantId） |
| `agents` | **可选收窄**：空/`*`=不限；显式列表=仅这些 agentId |
| `scopes` | `open` / `admin`；**空列表兼容旧配置不限制**（生产应显式声明） |

### 2.2 Scope 规则（`ApiKeyAuthFilter`）

| 路径 | 所需 scope | 说明 |
| --- | --- | --- |
| `/api/v1/health/**` | 无 | 就绪检查 |
| `/api/v1/admin/**` | **admin** | 管理台、治理、审计、配额、业务系统… |
| 其余 `/api/**`、`/v1/chat/**` | **open** | 对话、会话、流式、OpenAI 兼容 |
| Channel Webhook | 不走 API Key | `X-Channel-Token` 签名/令牌 |

- Open Key 调 admin → **403 `INSUFFICIENT_SCOPE`**
- `admin` **不隐含** `open`（`KeyEntry.allowsScope` 只 `contains`）
- 未知 Bearer 在 `amp.iam.issuer-uri` 启用时交给 JWT Resource Server（双轨）

### 2.3 身份优先级（`AuthContext`）

```text
JWT（SecurityContext） > Jeecg（X-Access-Token） > API Key（ThreadLocal）
```

- `requireTenantId()`：JWT 的 `tenant` → Jeecg 用平台配置租户（默认 acme）→ Key 的 `tenant-id`
- `requireAgent(agentId)`：仅当 Key **显式**配置了 agents 白名单时收窄；JWT 人身份不限制 Agent 白名单
- 人轨原始票可写入 `USER_TOKEN`，供 `authMode=user_token` 的工具透传业务侧

### 2.4 人轨 RBAC（`RbacGuard` / `IamService`）

适用：JWT / Jeecg 人身份调用带权限点的接口（编排、技能审核、IAM、计费等）。

**角色与默认权限点**（`IamService.defaultRolePerms`）

| 角色 | 权限点 |
| --- | --- |
| `tenant_admin` / `admin` | orch:read/write/run · iam:admin · billing:read/write · skill:review · agent:call · admin:read/write |
| `ops` | orch:* · admin:read/write · agent:call |
| `skill_reviewer` | skill:review · agent:call · admin:read |
| `auditor` | billing:read · admin:read · orch:read |
| `developer` | orch:* · agent:call · admin:read/write |
| `agent_caller`（默认） | agent:call |

**判定顺序（`RbacGuard.require(permission)`）**

1. API Key 带 **admin scope** → 直接放行（机器运维）
2. Jeecg：平台管理员 **或** `jeecg.hasPerm(permission)`（业务权限码）
3. 否则查 IAM：`userId` 的角色是否含该权限点
4. （可选）`amp.iam.trust-headers=true` 时信任 `X-User-Id` / `X-User-Roles`（迁移窗口）
5. 失败 → `403` `RBAC_DENIED` / `INSUFFICIENT_SCOPE`

> 注意：`X-User-Id` / `X-User-Roles` **默认不信任**；`iam_*` 表已有 schema，`IamService` 当前角色授权主要在内存（重启丢、多副本不一致）——生产化需落库。

### 2.5 前端（Console）

- 本地密钥存在 `localStorage`（`amp.console.auth`）
- 标准 SSO：无会话跳平台 IdP；请求头用平台 access_token
- 管理页与 `/api/v1/admin/**` 对齐，Open Key 打不开治理写操作

## 3. L2 · Agent 工具权限（Permission Rule）

### 3.1 数据模型

**`permission_rule`**

| 列 | 说明 |
| --- | --- |
| tenant_id + agent_id + tool_name | 作用域 |
| rule_content | 匹配参数；库中常为 `*`，**注入引擎前映射为 null（全匹配）** |
| behavior | `ALLOW` / `ASK` / `DENY` |
| source | `platform` / `console` / `suggested/session` 等 |

**`agent_permission_mode`**

| mode | 未命中规则时的默认 |
| --- | --- |
| `DEFAULT` | **每次询问**（ASK） |
| `DONT_ASK` | **一律拒绝**（不弹 HITL） |

### 3.2 构建与匹配（`GovernanceService.buildPermissionContext`）

1. 读 mode → `PermissionMode`
2. 读该 Agent 全部 `permission_rule`
3. `normalizeRuleContent`：`*` / 空 → `null`（引擎 `matchRule` 语义）
4. 注入 `PermissionContextState` → Agent 实例

**关键坑（已在 AGENTS.md 记录）**

- AgentScope `ToolBase.matchRule` 对非文件工具 **仅当 `ruleContent == null` 才匹配**；`"*"` 不是通配符  
  → 库里可存 `*`，但必须由 `normalizeRuleContent` 转成 `null`，否则 ALLOW/ASK/DENY 全失效，落到 mode 默认（DEFAULT=一直问 / DONT_ASK=一直拒）
- **同工具同内容行为唯一**：`upsertRule` 会删掉该工具其它 behavior（`DENY→ASK→ALLOW` 判定，并存 ASK 会盖 ALLOW）
- **变更即时生效三步**：①落库 `upsertRule`/`setMode` ②`evictTenant` 驱逐实例 ③`SessionStateRuleScrubber.resync*` 同步 Redis 会话状态  
  漏③时旧会话仍按旧规则判定

### 3.3 管理入口

| 入口 | 说明 |
| --- | --- |
| 控制台「权限与模式」 | 矩阵：Agent × 工具 → ALLOW/ASK/DENY |
| `POST /api/v1/admin/governance/permissions` | 单条 upsert |
| `POST .../permissions/batch` | 批量 |
| `POST .../permission-mode` | 设 DEFAULT / DONT_ASK |
| `GET .../permissions?agentId=` | 查询 |
| Agent 详情 / 小助 | 可读规则 |

### 3.4 建议规则（acceptRule）

- ASK 审批确认时可 `acceptRule=true`，把建议规则 **写入 `permission_rule`（source=suggested/session）** 并驱逐 + 状态重同步  
- 效果：同工具后续调用（含同租户其它会话）免问  
- 范围是 **租户级**（管理台可见可改）；仅引擎 `ConfirmResult.rules` 不会写入状态，**平台落库是生效主路径**

## 4. L3 · HITL 人工确认

| 场景 | 行为 |
| --- | --- |
| 工具 behavior=`ASK` | 调用前暂停，进 `approval_item` |
| 流式 `messages:stream` | `REQUIRE_USER_CONFIRM` 事件 |
| 非流式 `messages` / confirm | **`409 HITL_CONFIRM_REQUIRED`**（非空串） |
| OpenAI 兼容 `/v1/chat/completions` | 409 + OpenAI error 结构 |
| 重复确认 | `409 APPROVAL_ALREADY_RESOLVED` |
| 全部工具被拒 | `StopOnAllDeniedMiddleware` → `generateReason=ALL_TOOLS_DENIED` |

**确认接口**：`POST .../sessions/{sid}/confirm`  
**易踩坑**：confirm 必须回填 `ToolUseBlock.content`（JSON 字符串）；审批接口 `toolInput` 是 **JSON 字符串**，前端回传需 `JSON.parse` 后放进 `input`。

**审批中心**：`GET /api/v1/admin/inbox` · `POST /api/v1/admin/approvals/{id}/decide`（需 admin scope）

## 5. L4 · 工具侧鉴权与风险（ToolMeta）

HTTP/MCP 业务工具在 `business_tool.config` 携带安全元数据：

| 字段 | 含义 | 注册门禁（`ToolMeta.validateForRegistration`） |
| --- | --- | --- |
| `risk` | low / medium / high / forbidden | **forbidden 拒绝注册** |
| `authMode` | user_token / client / none | **client 不能调写方法**；**high 不能用 client** |
| `readOnly` | 只读 | GET/HEAD 默认 true |
| `permCode` | 业务权限码 | 透传给所属系统 |
| `ownerSystem` / `systemCode` | 所属系统 | 责任与划分 |
| `secretRef` | 密钥引用 | **config 禁止明文 Authorization/X-Api-Key** |
| `timeoutMs` / `maxRetries` / `rate_limit_qps` | 韧性 | 运行时 |

**调用时（`HttpBusinessTool`）**

- `authMode=user_token`：注入 `X-Access-Token` / `Authorization: Bearer`（用户票）→ **Agent 权限 ⊆ 用户在业务系统的权限**
- `secret:` 头：用 `secretRef` 查 `tool_credential` 注入
- 响应脱敏（password/token 等）、截断；只读失败可重试；连续失败熔断
- SSRF：`amp.tools.block-private-urls=true` 时拒内网 URL（本地默认关）

**Agent × 工具装配（`agent_tool_binding`）**

- 有绑定行：仅 `enabled=true` 的工具进 Toolkit  
- 无绑定行：兼容旧行为，挂载该租户全部 **ENABLED** 工具（再经 L2 规则过滤）

## 6. 业务系统划分（与权限的关系）

- `biz_system`：系统编码、名称、负责人、联系方式、状态  
- `agent.system_code` / `business_tool.system_code`：归属  
- **当前不替代权限**，用于：筛选、责任、后续系统级策略/配额/审计聚合  
- 删除系统时若仍有工具归属会 `SYSTEM_IN_USE` 拒绝

## 8. 配置速查

```yaml
amp:
  auth:
    enabled: true
    keys: [ ... open / admin ... ]
  iam:
    issuer-uri: ${AMP_IAM_ISSUER_URI:}    # 空 = 仅 API Key
    jwk-set-uri: ${AMP_IAM_JWK_SET_URI:}
    trust-headers: false                  # 默认不信任 X-User-*
  jeecg:
    enabled: false                        # pc_platform SSO 时打开
tools:
  # amp.tools.block-private-urls=true     # SSRF 严格模式
```

**常用错误码**

| code | 场景 |
| --- | --- |
| `INSUFFICIENT_SCOPE` | scope 不足 / RBAC 拒 |
| `RBAC_DENIED` | 人轨缺权限点 |
| `HITL_CONFIRM_REQUIRED` | 待人工确认 |
| `APPROVAL_ALREADY_RESOLVED` | 重复确认 |
| `TOOL_RISK_FORBIDDEN` | forbidden 工具 |
| `TOOL_AUTH_CLIENT_WRITE_DENIED` | client 调写接口 |
| `TOOL_SECRET_REF_REQUIRED` | 明文密钥头 |
| `SYSTEM_IN_USE` | 删除仍有工具的系统 |

## 9. 管理台操作路径

| 目标 | 路径 |
| --- | --- |
| Agent × 工具 ALLOW/ASK/DENY | 治理中心 → **权限与模式** |
| 工具风险 / 生命周期 / 试调用 | 治理中心 → **工具中心** |
| Agent 绑定哪些工具 | 工具详情 → **Agent 装配** / 授权矩阵 |
| 业务系统 | 治理中心 → **业务系统** |
| HITL 审批 | 工作台 → **审批中心** |
| 角色授权 | 治理中心 → **IAM / RBAC** |
| 审计 | 运营中心 → **审计** |

## 10. 推荐落地策略（多系统接入）

1. **系统**：先建 `biz_system`，工具/Agent 挂 `systemCode`  
2. **机器 Key**：业务集成用 `open`；仅运维台用 `admin`；必要时 `agents` 白名单收窄  
3. **工具**：只读 `risk=low` + `user_token`；写接口 `medium/high` + 默认 ASK  
4. **规则**：只读 ALLOW、写 ASK；确认后按需 acceptRule 固化  
5. **人轨**：开 Jeecg/JWT 后用角色（agent_caller / skill_reviewer…），勿开 `trust-headers` 除非迁移  
6. **变更**：改权限必须落库 + 驱逐实例 + 会话状态重同步

## 11. 已知边界 / 待增强

| 项 | 现状 | 建议 |
